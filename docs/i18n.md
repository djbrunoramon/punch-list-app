# Internationalization (i18n)

The app is translated into **English (`en`, base and fallback)** and **Brazilian Portuguese (`pt-BR`)** with
[Transloco](https://jsverse.gitbook.io/transloco) 8.4, so the language changes at runtime without a reload.

## How it works

| Piece | File | Role |
|---|---|---|
| Language service | `src/app/core/i18n/language.ts` | Current language (signal). The first visit uses the browser language (`pt*` becomes `pt-BR`, anything else `en`). The choice is saved in `localStorage` (`lang`), and the service updates `<html lang>` and Transloco. |
| Switcher | `src/app/core/i18n/language-switcher.ts` | EN / PT-BR buttons in the header. |
| Loader | `src/app/core/i18n/transloco-http-loader.ts` | Loads `public/i18n/<lang>.json` (served by the app, not by the API). |
| API language | `src/app/core/i18n/accept-language.interceptor.ts` | Every request sends `Accept-Language: en` or `Accept-Language: pt-BR`. The API answers problem details (`title`, `detail`, `errors[].message`) in that language, and the app shows them as they come. |
| Taiga texts | `src/app/core/i18n/taiga-language.ts` | `TUI_LANGUAGE` follows the app language (`english` / `portuguese` from `@taiga-ui/i18n`). |
| Tab title | `src/app/core/i18n/translated-title-strategy.ts` | Route `title` values are keys; the tab shows `<page> · <app.name>`. |
| Dates and currency | `Language.locale()` | Passed to the `date`/`currency` pipes (`en-US` / `pt-BR`). `estimatedAt` stays in BRL. |
| Form messages | `src/app/shared/util/validation-messages.ts` | Language-reactive Signal Forms messages (`validation.*`). |

## Key naming standard

### General rules
1. **A key describes the purpose, never the text**: use `common.action.save`, not `common.saveButton` or `common.salvar`.
2. **Dot hierarchy from general to specific**: `<scope>.<area>.<element>[.<variant>]`, at most 5 levels.
3. **Segments in lowerCamelCase, English, ASCII only** (`responsiblePersons.list.empty`). The only exception is
   **enum values**, which keep the exact API value (`enum.pendencyStatus.CLOSED`).
4. **Field name = API field name** (camelCase from the request or response): `contracts.field.numberContract`. List columns
   and form labels share the same field key.
5. **Interpolation only through named parameters** (`{{ max }}`), never by concatenating translated pieces.
6. **One key, one meaning.** Do not reuse a key because two texts happen to be equal. Truly shared texts go under `common.*`.
7. **Dynamic keys only for enums** (`'enum.pendencyStatus.' + status`). Everything else uses literal keys, so search and
   extraction keep working.
8. **No missing or orphan keys**: every language file has the same keys. A test enforces this (see below).
9. **`en` is the base language** (source of truth and fallback). A new key is added to `en.json` first.
10. **Files**: `public/i18n/<locale>.json`, as nested objects with keys sorted alphabetically at every level.
11. **Locales in BCP 47**: `en` and `pt-BR`, in the files and in the `Accept-Language` header.

### Scopes
| Scope | Use | Examples |
|---|---|---|
| `app.*` | app identity | `app.name` |
| `common.action.*` | reusable button and link verbs | `common.action.save`, `common.action.cancel`, `common.action.edit`, `common.action.retry`, `common.action.addContract` |
| `common.state.*` | generic page states | `common.state.loading`, `common.state.empty` |
| `common.label.*` | generic labels | `common.label.actions`, `common.label.status`, `common.label.pagination` |
| `shell.*` | header: navigation, contract selector, theme, language | `shell.nav.dashboard`, `shell.contractSelector.label`, `shell.theme.toDark`, `shell.language.label` |
| `<feature>.*` | one scope per feature: `contracts`, `responsiblePersons`, `pendencies`, `dashboard` | see below |
| `validation.*` | form validation messages | `validation.required`, `validation.maxLength` (`{{ max }}`), `validation.min` (`{{ min }}`) |
| `error.*` | client and network errors, used when the response is not a problem detail | `error.network`, `error.serverUnavailable`, `error.unexpected`, `error.title.requestFailed` |
| `enum.<enumName>.<VALUE>` | labels of API enums | `enum.pendencyStatus.OPEN` |

### Inside a feature
| Pattern | Example |
|---|---|
| `<feature>.title` | `contracts.title` (page heading and route title) |
| `<feature>.field.<apiField>` | `contracts.field.estimatedAt` (list column and form label) |
| `<feature>.list.new` / `.list.empty` / `.list.emptyAction` | list actions and empty state |
| `<feature>.list.<other>` | anything else specific to the list (`contracts.list.active`) |
| `<feature>.form.title.create` / `.form.title.edit` | form heading and route title |
| `<feature>.form.<other>` | anything else specific to the form (`contracts.form.estimatedAtBrl`) |
| `<feature>.message.<event>` | feedback and notices (`pendencies.message.selectContractToCreate`) |

## Using translations
- **Templates**: use the `transloco` pipe, as in `{{ 'contracts.title' | transloco }}`, or with parameters,
  `{{ 'validation.maxLength' | transloco: { max: 50 } }}`.
- **Attributes**: bind them, as in `[attr.aria-label]="'shell.nav.label' | transloco"`.
- **TypeScript**:
  - text that must follow language changes: `translateSignal` or `translateObjectSignal` (see the status `stringify` in
    `pendency-form.page.ts`);
  - one-off text (for example a submit error): `TranslocoService.translate`.
- **Forms**: `private readonly message = injectValidationMessages();` gives `{ message: this.message('validation.required') }`.
- **Never** use `innerHTML` with translations; the lint blocks it. Parameters are rendered as text (tested).

## Adding a key
1. Pick the scope and name following the standard above.
2. Add it to `public/i18n/en.json`, then to `public/i18n/pt-BR.json`, keeping the alphabetical order.
3. Use it in the template or code.
4. Run `npm test`. The translation-file spec fails if a key is missing in one language, if a value is empty, if the
   parameters differ, if a key breaks the naming standard or if the order is wrong.

## Adding a language
1. Add the code to `APP_LANGUAGES` and `LOCALE_BY_LANGUAGE` in `language.ts`, and map the browser language in
   `languageFromBrowser`.
2. Create `public/i18n/<code>.json` with every key.
3. Add the Taiga language in `taiga-language.ts` and `registerLocaleData` for the locale in `app.config.ts`.
4. Add the switcher labels (`shell.language.*`) and the file to `TRANSLATIONS` in `src/testing/i18n.ts`, so the parity
   test covers it.
5. Make sure the API also supports the language (its `messages_<locale>.properties`).

## Tests
- `src/app/core/i18n/translations.spec.ts` checks parity, non-empty values, parameters, naming and order.
- `language.spec.ts`, `accept-language.interceptor.spec.ts`, `taiga-language.spec.ts`, `translated-title-strategy.spec.ts`
  and `translation-escaping.spec.ts` (AM-I2) cover the infrastructure.
- Specs render the real `en.json` through `provideI18nTesting()` (`src/testing/i18n.ts`), so they assert on the English
  texts users see.
